---
name: Daily managed streaming
description: Why StecStats Live uses Daily cloud recording and the durability/security rules that must remain intact.
---

StecStats Live uses Daily as the sole camera owner on mobile. The iPad publishes through Daily, Daily records the authoritative cloud master, and Daily sends one RTMPS output to an unlisted YouTube Live broadcast. Public viewers watch the Daily feed through the account-free StecStats share link so the app can render its live scoreboard over the video; YouTube remains the external feed/archive. The API imports the finalized Daily master into App Storage before generating reels. Do not reintroduce simultaneous HoopsCamera recording or custom WebRTC/MJPEG publishing during a Daily session. Daily's call object is headless: the scoring screen must render its local participant video track through `DailyMediaView`; disabling HoopsCamera alone otherwise leaves a black preview even while capture is active.

**Why:** The custom simultaneous local-recording and livestream paths repeatedly failed on physical iPads. Managed cloud recording removes competing camera ownership. The channel rejected third-party YouTube playback even after its API reported the video as embeddable, so the branded page cannot depend on a YouTube iframe if it must show both video and scoreboard. A physical viewer test confirmed that direct Daily playback on the branded page successfully shows the video and StecStats scoreboard together.

**How to apply:** Persist the live-session-to-game association in the same durable game-save operation, including offline retries. Keep broadcaster signaling authenticated and session-bound. Issue receive-only Daily tokens to public share-page viewers while the room is active; keep scoreboard updates on the existing public socket without an artificial YouTube delay. Render only Daily's local track while a Daily session is active; route camera flip and microphone controls through Daily's call object. Do not show a preview-only zoom control that would misrepresent the outgoing stream. Never use Daily's `single-participant` recording/RTMP layout without the participant `session_id`; a missing target can be accepted while producing a zero-duration recording and no YouTube frames. For one coach, use the default recording layout, but omit the layout object from the REST live-streaming request: Daily's production REST endpoint rejected documented `max_cam_streams`. Never treat every Daily 400 as idempotent success; only suppress an explicit already-active/already-stopped response. Keep YouTube start/finalization retryable and fenced. Use renewable token-fenced leases for long recording imports.
